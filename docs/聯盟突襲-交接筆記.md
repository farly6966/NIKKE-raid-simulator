## 2. 使用者要做什麼

**公會（32 人）的聯盟突襲排班表。**

他手上已經有一份 Excel（`工作表2 (排序)`），長這樣：

| 名称 | 同步器等级 | 水 | 电 | 风 | 火 | 铁1 | 铁2 |
|---|---|---|---|---|---|---|---|
| 藤原妹洪 | 698 | 1 | | 1 | 1 | | |
| KE32 | 774 | 1 | | 1 | 1 | | |

格子裡的 `1` = 這個人要打這隻王，空白 = 不打。**他要的是把那個 `1` 換成實際算出來的傷害。**

流程：成員各自匯出 JSON → 會長一次全部拖進網站 → 每隻王排好一套隊 → 算 → 出分配表 → 下載貼回 Excel。

### 王的數量是 6 不是 5

聯盟突襲有五隻王（五屬性各一）。**全部階段打完後，第五隻王會進入「無限階段」（血量無上限），那時全公會只能打那一隻。** 所以排班表上第五隻王佔兩欄（他表上的 `铁1`/`铁2`）。每一期第五隻王的屬性都不同。

## 4. 已經做完的東西

### 資料進來的路

| 檔案 | 做什麼 |
|---|---|
| `site/src/exia-import.ts` | **Exia 匯出檔 → 計算機規格**。新舊兩種格式都吃 |
| `site/src/exia-import.test.ts` | 19 條測試，含 3 條釘住「cookie 不外流」 |
| `scraper/profile_import.py` | 同一件事的 Python 版（本機批次用） |

**Exia = ExiaInvasion R**，一個 Chrome 擴充功能，從 blablalink 匯出自己帳號的養成資料成 `<名字>_<uid>.json`。

**設計原則（重要）**：`exia-import.ts` **只翻欄位名**，翻譯規則一律交給既有的 `blablalink.ts` 的 `areaToOverrides` / `consoleFrom` / `synchroFrom`。那三個函式一行都沒改。理由：樂島 CSV、blablalink、Exia 三條路要落在同一個位置，不然同一個帳號會算出三種規格。

**兩個必須換算的坑**：
1. **數值差 100 倍**：blablalink 給 `1802` 代表 18.02%，Exia 直接給 `18.02`。合成 `state_effects` 時要先 ×100
2. **超載選項要合成 id**：blablalink 是「裝備欄存 id、另一張表查效果」，Exia 把效果寫在裝備欄裡。要替每種（效果, 數值）發流水號再組回那張表，**從 1 開始**（0 在那邊代表空欄）

**兩種 Exia 格式**（沒有版本號，靠鍵名分辨）：

```
新（2026-08 起）  equipments: { head: { tier, lv, options: [[線],[線],[線]] }, ... }
                  recycleRoomResearches: { "1001": { Level: n }, ... }
                  有 cube_id / cube_level / attractive_lv

舊（~2026-09-02） equipments: { "0": [線, 線, 線], ... }   ← 0/1/2/3 = 頭/身/手/腳
                  researchLevels: { general: n, attacker: n, ... }
```

**憑證處理**：匯出檔裡有 `cookie`（含 `game_token`）和 `game_uid`。程式從頭到尾不讀。另外有 `stripExiaProfile()` 給使用者在**傳檔之前**洗檔用（白名單，不是黑名單），順帶把 489KB 縮到 103KB。

### 畫面

| 檔案 | 做什麼 |
|---|---|
| `site/src/union-squad.ts` | 視覺排隊器：五格 + 角色格柵（搜尋 + 屬性/職業/爆裂篩選） |
| `site/src/union-raid.ts` | 聯盟分頁主體。匯入、王的盤面、執行、分配表 |

**為什麼另寫排隊器而不共用計算機的**：`ui.ts` 的 `renderSquad` 是 248 行，牽連 15 個閉包（`renderEditor`、`renderCharacterSettings`、`openCharPanel`、`saveState`…），抽出來等於對 app 核心動手術。而**聯盟的隊伍只需要五個名字** —— 養成全部來自各成員的檔案，在這裡放養成編輯器反而是誤導。樣式沿用既有的 `.roster-*` 類別。

**角色格柵只有一個**，會移動到「正在編輯的那一列」下面。⚠️ 掛 DOM 的動作必須在 `renderSlots` 裡做，不能在 `open()` 裡 —— 因為開啟後馬上會整塊重畫，在 `open()` 掛的會被扯掉。有測試釘住。

### 分配表

`buildGrid()` / `gridToCsv()`（都在 `union-raid.ts`，純函式好測）

- 列是人、欄是王，依**總貢獻**排序
- **空白分兩種**：沒指派（格子不存在）vs 指派了但缺角色（寫出缺誰）。填 0 會被讀成「打了但零傷害」
- CSV **帶 BOM**，不然 Excel 開中文會亂碼
- 數值是**原始整數**，寫成「億」Excel 會當文字，不能加總排序

| `site/src/union-raid-planner.ts` | 把「誰打哪隻王、用哪一隊」寫成 MILP 交給 HiGHS |
| `site/src/union-planner.worker.ts` | 在 Worker 裡跑 HiGHS（`time_limit: 30`·`mip_rel_gap: 0.00001`·`random_seed: 44`） |
| `site/src/union-raid-live.ts` | 現場確認一刀之後，**整題重解**（不是增量修補） |
| `site/src/union-raid-live-view.ts` | 實戰推演分頁的畫面 |

**求解順序**：第 1 階段 → 第 2 階段 → 第 3 階段 →（三階段全清才進）無限五王 →
最後一次「減少尾刀溢傷」。所以 `time_limit` 是**每一次求解**的上限，最多乘五。

#### 實測數據（2026-09-20，使用者的真實盤面）

**拉長 `time_limit` 完全沒用。** 21 人的盤面，30 / 120 / 300 秒三組結果一字不差
（都停在第 3 階段、都超時、無限階段傷害 0）。**別再試 500 秒。**

**放寬 `mip_rel_gap` 本來會更糟 —— 那是個潛伏缺陷，已於 2026-09-20 修掉。**
階段推進的判定本來是

```ts
if (solution.ObjectiveValue < required - 0.5) break;
```

**它拿一個「容許 gap」的目標值去比一個精確門檻。** gap 設 2% 時 HiGHS 回的解可能是
`0.98 × required`，這行就判「清不完」直接 break，**整個規劃安靜地只做第 1 階段**。
實測 gap 2% 與 5% 都在 1 秒內收工然後停在第 1 階段。所以 `0.00001` 不是調過頭，
**它是在替這行擦屁股**。

現在改成用**上界**比：給了 gap 的 HiGHS 回報的 incumbent `z` 最多比真最佳低 gap，
所以真最佳 `z* ≤ z / (1 - gap)`，拿這個上界去比門檻。`HighsSolution` 沒有 dual bound
可讀（只有 `Status`·`ObjectiveValue`·`Columns`·`Rows`），所以由 gap 反推。
worker 把 gap 同時交給求解器和排刀器（`optimizeRaidPlan(..., relGap)`）—— **不交就等於
沒修**。回歸在 `union-raid-planner.test.ts`：小樣本下 HiGHS 給了 gap 也照樣找到精確解，
所以測試**改用「把目標值削 3% 的假求解器」**模擬 gap 容忍解，不靠 HiGHS 的心情。

**「從來沒摸到無限階段」不是 bug，是人數不夠。**

```
三階段總血量           30,778 億
21 人實際打得出         27,633 億   ← 差 3,145 億，清不完
21 人的天真上界         34,458 億   ← 灌水：忽略了「一個人的三隊不能共用同一隻妮姬」
32 人 → reached: endless，96/96 刀全排滿，無限階段 8,942 億
```

順帶一提，**問題越接近可行性邊界越難解**：21 人（差 3,145 億）要 120 秒還證不出來；
32 人（餘裕 72%）三個階段加起來 **1 秒**。

#### 尾刀溢傷那一趟只給小預算（2026-09-20 修）

那一趟是**有結果最好、沒有也無妨**的：超時就退回超時前的解
（`const final = tie.Status === 'Optimal' ? tie : primary;`）。給大預算等於燒多少丟多少。
32 人盤面實測原本 42 秒裡有 30 秒是它。

現在 `MilpSolve` 可以接一個**只給這一判**的預算（`TIE_BUDGET_SECONDS = 5`），
前面的階段求解仍用呼叫端的預設值。

```
          5 秒版   18 秒
          30 秒版  42 秒
出刀組合   逐項完全相同（96 刀全比過）
```

快就賺到，不快就早點收手。**縮短前先證明方案沒變** —— 那個比對是這一改的合格門檻。

#### 還沒修的一件

**每確認一刀都 `new Worker`**（`union-raid-live-view.ts` 的 `resolve()`）。HiGHS 在
worker 裡是**同步阻塞**的，跑起來沒辦法中斷，所以「砍掉重開」**就是取消機制** ——
不是疏忽，不能只是改成重用。要動得另外設計（例如養一個預熱好的備用 worker）。
第一次進分頁時會卡約 70 秒在「正在重新計算…」，那是在下載 HiGHS 的 wasm；
之後有瀏覽器快取。**重開一次到底多貴還沒量過，沒量就不要動。**

#### 實戰推演分頁的三項修正（2026-09-20）

- **記錄表單本來不看建議** —— 成員照名字排序、隊伍取候選清單第一筆。那**不是**方案選的
  隊。照著按下去會記到沒鑽過的編成，而「一個人不能重複用同一隻妮姬」的排除是讀
  `shot.squad` 算的，於是後面的建議整片歪掉，**而且不會報錯**。現在表單預選建議的人與
  隊，晶片上有「建議」標記。
- **頂端「目前各王下一刀建議」本來只能看** —— 要按得往下捲過一張 21×5 的表。現在每一列
  就有預填傷害欄與確認鈕。
- **畫面本來只顯示當前階段的刀**（`member.shots.filter(s => s.phase === now)`）——
  第 1 階段只用到 14 刀，所以其他人看起來全是 `0/3`、什麼都沒排，**實際上他們的刀在第
  2、3 階段**。新增「每個人要出的刀」卡片，**跨階段**列出每人三刀並標階段。
