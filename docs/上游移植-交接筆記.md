## 1. 這個 repo 跟 upstream 的關係（先看這段，不然會走冤枉路）

這個 fork **不是** `Jgaram/nikke-calc` 的 fork。

```
git merge-base ce75361 upstream/master   →  沒有共同祖先
git merge-base ce75361 Moris-kr/master   →  f56124d
```

歷史來自 `Moris-kr/nikke-calc`；`Jgaram/nikke-calc` 是同一個專案用新歷史重新發佈的
那一邊（第一個 commit 是 2026-08-23 的部署快照）。兩邊會互相搬對方的修正，所以
**同一個缺陷常常已經用不同的實作在各自那邊修好了**。

推論：

- **不要 cherry-pick。** 曾經直接 cherry-pick `5abe65e` 就撞衝突。逐筆讀 diff 做語意移植。
- **逐行比對只能拿來分類（triage），判定一律看語意。** 上游新增的 5 行程式碼在 fork
  裡可能全都有，但在**別的路徑**上，真正該修的那條是空的（`63a784e` 就是這樣）。
- **名字不一樣不代表沒有。** 例：upstream 的 `infinite_ammo`，fork 早就有，叫
  `max_ammo_infinite`。

### 判定基準（沿用 `context/UPSTREAM-MAPPING.md`）

| 判定 | 意思 |
|---|---|
| 已存在 | 同一個缺陷在 fork 已經修好了。實作不同也算 |
| 部分 | 本體有，只缺後續補強 |
| 需移植 | 這個缺陷在 fork 還活著 |
| 不適用 | 在 fork 的結構下不成立 |
| 已移植 | 做掉了，附 commit |

#### `ac8fe2a` — 控制的「何時」收成錨點語法（B 區 · fork `716f1a1`）

`_CLICK_WINDOWS` 本來是「每來一個新需求就多一個名字」的列舉，而同一個形狀的
「錨點 + 偏移」以不同名字散在五個地方（裝填控 A·B·C · 長按控 · `hold_judge`）。
統一成兩個表記：

    時刻 = anchor + offset − minus
    點擊：[時刻, 時刻+len) 區間   /   掩體：t >= 時刻 的進入觸發

**沒有把狀態窗拿掉，這是關鍵。** `burst_charge` 不是錨點+偏移而是狀態 ——
它判的是 `state["burst_gauge_charging"]`，正好是 `add_burst_gauge()` 用來決定充不充的
同一個值。換算成時刻，「點擊區間與充電區間不可能錯開」這個保證就沒了。

**錨點自己帶著閘門，這是零回歸的根據。** A·C 的 `full_burst` 要求與 B 的觀測值要求
都收進錨點定義裡，判定式一個字都沒變。`full_burst_end_t` 是 Full Burst 結束後還留在
state 裡的值，沒有閘門的話「結束前 0.3 秒」會從那之後永遠為真。

目錄是**關起來的**（`_ANCHORS` 五種）。表達力一變大就容易生出「被安靜忽略的輸入」，
所以詞彙檢查集中到 `validate_control()` 一處，組裝與 doclint 呼叫同一個函式，
並立了 doclint 檢查 I —— `_control_rules` 要條件符合的編成才會走到組裝，
**沒人跑過的規則**的錯字只有在那裡抓得到。

fork 比上游多做兩件：`reload.len` 不再被安靜丟掉（上游只挑 `anchor`·`offset`·`minus`
往下傳，所以「掩體不是區間」那條檢查根本到不了）；떼기 模式不准掛 `combat_start` 錨點。

#### `cf8c9ec` 剩的兩件 —— 執行期閘門與自身增益到期（B 區 · fork `cdafa45`）· **B 區全清**

同一個 upstream commit 裡的 `burst_chain` + `hold_until_close` 不靠錨點，先走了 `0452e4b`。

兩件都在擴大「何時」，但守著**觀測不會改變戰鬥**這條線：

- **執行期閘門** `gate: {burst_stage, burst_user}` —— 不是自由條件式，是看**已經確定**的
  這一循環各階段爆裂使用者的封閉詞彙。不預測「接下來誰會用」，所以這個閘門改不了循環本身。
  記錄在**進入下一循環第 1 階段時**清空 —— 在結束那一 tick 清的話，卡在 Full Burst
  **結束前**的裝填控與**結束後** `burst_charge` 窗裡的點擊會看到不同的 B3 使用者。
- **`own_buff_end` 錨點**（+ 裝填控政策 D `finish_by_own_buff_end`，等級中）——
  自己發動的具名有限增益的到期時刻。**不去查效果的對象**是核心：延遲 resolve 的增益
  若被提前確定對象，就會單因為「控制看了一眼」而讓戰鬥結果改變。

fork 再多一件：**用名字指的東西存不存在會被檢查**（`_check_control_refs()`）。
`gate.burst_user` 不在編成裡、或 `buff` 不在那隻妮姬的技能效果裡，`simulate()` 開跑前就斷。

`site/scripts/sync-runtime.mjs` 的 `manifest.version` 是檔案內容的 sha256 前 16 碼，
而它 **把換行也算進去**。這台機器是 Windows（CRLF），CI 是 Linux（LF），所以
**同樣的內容在兩邊一定會算出不同的 hash**。

2026-09-18 實測過一次：線上 `3928534973d4366e` vs 本機 `762216b509b25874`，25 個檔案
有 22 個不同——逐位元組比對後，每一個差異的位元組數**正好等於該檔的 CRLF 數量**，
語意完全相同。差點被誤判成部署失敗。

所以線上驗證要看**內容**不是 hash：

```bash
# ① 有沒有出過新的一版（只證明這個，不證明你的改動在裡面 —— 理由見下）
curl -s https://farly6966.github.io/NIKKE-raid-simulator/ | grep -oE 'assets/index-[A-Za-z0-9_-]+\.(js|css)'
# ② 引擎改動真的上去了沒 —— 抓線上 runtime 的原始碼找標記。**這一條才是證明**
curl -s https://farly6966.github.io/NIKKE-raid-simulator/runtime/calculator/timeline.py | grep -c '_reenter_done_stages'
# 前端改動的話同理，抓 bundle 找標記
curl -s https://farly6966.github.io/NIKKE-raid-simulator/assets/index-XXXX.js | grep -c 's44-laitance'
```

⚠️ **資產指紋一定會變，就算一個字都沒改。** `site/vite.config.ts` 裡
`__BUILD_ID__ = Date.now().toString(36)`，經 `define` 烤進 `worker-client.ts`
（給 `calculator.worker.js` 當快取破除參數），所以**每次 build 都是新 hash**。

2026-09-19 實測：一次**純文件**的 commit（`e9d2205`，程式碼零改動）照樣把指紋從
`index-r1Ao8TLX.js` 換成 `index-CqTEqjz6.js`。

所以①是「有新版上去了」的訊號，**不是**「我的改動在裡面」的證明 —— 證明要靠②。
反過來仍然成立：**指紋沒變就是沒部署**。

**待辦（小）**：讓 `sync-runtime` 在算 hash 前把換行正規化成 LF，這個陷阱就消失了。
