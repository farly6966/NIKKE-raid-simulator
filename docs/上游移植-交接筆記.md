## 1. 這個 repo 跟 upstream 的關係（先看這段，不然會走冤枉路）

這個 fork **不是** `Jgaram/nikke-calc` 的 fork。

```
git merge-base ce75361 upstream/master   →  沒有共同祖先
git merge-base ce75361 Moris-kr/master   →  f56124d
```

歷史來自 `Moris-kr/nikke-calc`；`Jgaram/nikke-calc` 是同一個專案用新歷史重新發佈的
那一邊（第一個 commit 是 2026-08-23 的部署快照）。兩邊會互相搬對方的修正，所以
**同一個缺陷常常已經用不同的實作在各自那邊修好了**。

推論：

- **不要 cherry-pick。** 曾經直接 cherry-pick `5abe65e` 就撞衝突。逐筆讀 diff 做語意移植。
- **逐行比對只能拿來分類（triage），判定一律看語意。** 上游新增的 5 行程式碼在 fork
  裡可能全都有，但在**別的路徑**上，真正該修的那條是空的（`63a784e` 就是這樣）。
- **名字不一樣不代表沒有。** 例：upstream 的 `infinite_ammo`，fork 早就有，叫
  `max_ammo_infinite`。

### 判定基準（沿用 `context/UPSTREAM-MAPPING.md`）

| 判定 | 意思 |
|---|---|
| 已存在 | 同一個缺陷在 fork 已經修好了。實作不同也算 |
| 部分 | 本體有，只缺後續補強 |
| 需移植 | 這個缺陷在 fork 還活著 |
| 不適用 | 在 fork 的結構下不成立 |
| 已移植 | 做掉了，附 commit |

## 2. 這一輪做了什麼

### `d85ac2f` —「彈藥 N% 移除」把彈匣打成負數

`93ec10a` 殘留項之一。`ammo_charge_pct` 扣的是**最大裝彈**的比例，不是彈匣裡現有的彈。
半滿的彈匣吃到 -100% 會變負數，接下來的裝填先花掉幾發爬回 0。

fork 裡吃到 -100 的五個都是會進編成的角色：그레이브「방열」· 라플라스 : 얼티밋
히어로「일렉트릭 파워 풀 풀 차지 5」· 밀크 : 블루밍 바니「부끄러움 3」· 질
「슈퍼 캅 2」· 드레이크 : 그레이트 빌런「오버 오버 드라이브 2」。

實測（질，「슈퍼 캅 2」掛在 `burst_cast`，每循環必定發生，120 秒）：
修正前彈匣最低 **-20**，四次進負數；修正後最低 0。

`handle_ammo_charge_flat` 沒動 —— 資料裡沒有負的 flat 值，上游也只在 pct 加了下限。

### `7cf88f8` — 有限掩體到期就收掉裝填

`35d8c20` 的掩體那一半。`_finish_reload` 的 docstring 本來就記著這個缺口。

**位置比實作重要**：照抄進 `_tick_cover` 是死碼 —— `tick()` 的裝填完成檢查在它前面，
而且裝填進行中就 `return []`。所以抽成 `_expire_timed_cover()` 放在那個檢查**之前**。
第一版就是加錯位置，靠測試抓出來的。

### `997170e` — 首循環也有「下次 Full Burst 開始」預測（B 區）

`c751e2a` + `54e30af`。政策 B(`into_fb`) 與 `if_dry` 靠**前一循環週期觀測**回答
「下次 Full Burst 何時開始」，第一循環沒有觀測值就整個不作用。改成用剩餘爆裂冷卻
把階段鏈 1→2→3 往前推。

**觀測贏過鏈條** —— 鏈條看不到還沒撒下的 `burst_cooldown_reduce`（技能撒的即時效果，
不是 buff），所以只在沒有觀測時當 fallback，而且**只在 Full Burst 結束那一刻取一次**
（每 tick 重取會讓「每循環一次」的守衛失效，掩體會連開）。

實測 `레이드_작열짬`：預測誤差 **+0.020 秒**，掩體 10 → 11 次（多的就是第一循環那一次）。

### `8ae5faf` — 클릭 스케줄 `control.click`（B 區）

`8d16ea5` 的클릭 스케줄部分。톡톡이 與 홀드 是**同一次左鍵上的兩個行為**，合併成一份
清單，**先匹配者勝**。窗四個 × 模式三個，詞彙是封閉的。舊鍵 desugar 接住，
**basline 29/29 一格都沒動**。

順手拿掉 `_tick_charge` 裡重複的 `_hold_release_t < 0` 守衛 —— 按下的決定已經在
charge 開始時 latch，留著會讓排程順序失去意義（反轉順序結果相同，測試抓到的）。

### `44b84c6` — 조작자는 한 명（B 區）

`8d16ea5` 的조작 모드部分。實際操作是**選中一隻妮姬**後左鍵／shift；計算機原本讓多人
同時操作直接通過，`context/CONTROL.md` §미구현·보류 把它記成「同時控制 1 人約束 ——
不檢查」，`레이드_라피앨리스` 的註解也自稱「樂觀上限」。

**關鍵是把判定與執行拆開** —— 仲裁必須能在沒有副作用的情況下問政策「你現在想要嗎」。
一個函式兼兩件事的話，「只是問一下」就會把掩體打開。`_arbitrate_control()` 在
char tick **之前**跑（在裡面決定的話隊伍位次會改變答案）。

baseline `레이드_라피앨리스` +0.10%。舊行為把相機退回 3 號位 = 라피（**MG，非蓄力**），
×2.5 滿蓄力量表倍率掛在永遠用不到它的人身上 180 秒；現在跟著實際操作者走
（앨리스 99.7%、라피 0.3% ≈ 0.47 秒）。full_burst 次數 15 → 15 不變，是循環內重分配。

**前端長測試不要和 Python snapshot 並行** —— 搶 CPU 會造成 `vi.waitFor` 假逾時

`python -m context.snapshot --update`。**不可為了綠燈直接接受未知差異。**

### 上線驗證：不要用 runtime version 比對本機與線上

`site/scripts/sync-runtime.mjs` 的 `manifest.version` 是檔案內容的 sha256 前 16 碼，
而它 **把換行也算進去**。這台機器是 Windows（CRLF），CI 是 Linux（LF），所以
**同樣的內容在兩邊一定會算出不同的 hash**。

2026-09-18 實測過一次：線上 `3928534973d4366e` vs 本機 `762216b509b25874`，25 個檔案
有 22 個不同——逐位元組比對後，每一個差異的位元組數**正好等於該檔的 CRLF 數量**，
語意完全相同。差點被誤判成部署失敗。

所以線上驗證要看**內容**不是 hash：

```bash
# 資產指紋換了沒（這個可靠 —— runtime version 有嵌進 JS bundle，內容一變 hash 就變）
curl -s https://farly6966.github.io/NIKKE-raid-simulator/ | grep -oE 'assets/index-[A-Za-z0-9_-]+\.(js|css)'
# 引擎改動真的上去了沒 —— 抓線上 runtime 的原始碼找標記
curl -s https://farly6966.github.io/NIKKE-raid-simulator/runtime/calculator/timeline.py | grep -c '_reenter_done_stages'
```

**待辦（小）**：讓 `sync-runtime` 在算 hash 前把換行正規化成 LF，這個陷阱就消失了。
